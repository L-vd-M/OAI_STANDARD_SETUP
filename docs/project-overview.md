## Background: What is OpenAirInterface?

**OpenAirInterface (OAI)** is a fully open-source, production-grade implementation of 4G LTE and 5G NR wireless network software, developed and maintained by the **OpenAirInterface Software Alliance (OSA)**. The OSA is a French non-profit founded at EURECOM (Sophia Antipolis, France) in 2014.

### Key facts

- **License:** OAI Public License V1.1 (based on Apache 2.0, with an additional clause requiring commercial users to join the OSA)
- **Academic use:** Completely free — no membership required for university research
- **Community:** Described by OSA as the "fastest-growing open-source community in cellular wireless"; strategic members include Ericsson, Nokia, and others
- **Recent partnerships:** OAI + Canonical (Ubuntu) for Open RAN (September 2024)
- **Standards compliance:** 3GPP Rel-15/16/17 for NR; Rel-10/12/14 for LTE

### What makes it unique for research

OAI is the only widely-adopted open-source platform where you can trace a single piece of data from a scheduler decision at the MAC layer all the way to a transmitted IQ waveform at the PHY layer, and from there through the 5G Core Network's NF chain. This makes it uniquely suited for:

- **PHY-layer algorithm research:** Custom waveforms, channel estimation, beamforming
- **Scheduling experiments:** New MAC schedulers with real air-interface feedback
- **Core network modification:** New SBI APIs, custom NF behaviour, policy experiments
- **O-RAN and RIC research:** E2 xApp development using FlexRIC (fully integrated)
- **End-to-end 5G evaluation:** All NFs + gNB + UE run in software on a single workstation using RFsimulator

The three main project pillars are: **OAI RAN** (gNB/eNB + UE), **OAI Core Network** (all 5GC NFs), and **OAI OAM** (O1 interface, FlexRIC nearRT-RIC).

```

  ▼             ▼

  │ N2 (NGAP)     ▲ E2AP
  ▼               │

  ├── UDM       NSSF
```

## Build & Deployment Notes

### RAN Build

```bash
cd OAI_RAN_code/openairinterface5g
# Install dependencies
cd cmake_targets && ./build_oai -I   # install dependencies
# Build gNB
./build_oai --gNB -w USRP            # with USRP frontend
./build_oai --gNB -w SIMU            # with RFsimulator
# Build NR-UE
./build_oai --nrUE -w USRP
```

Build output goes to `cmake_targets/ran_build/build/`.

### CN5G Deployment (Docker Compose via `oai-cn5g-fed`)

The federation repository (`oai-cn5g-fed`) contains Docker Compose files for complete 5GC deployment. The typical minimal stack:

```
oai-cn5g-upf ─ N4/PFCP ─ oai-cn5g-smf
                               │
oai-cn5g-nrf ◄─ all NFs register
oai-cn5g-amf ◄─ N2/NGAP from gNB
oai-cn5g-ausf, oai-cn5g-udm, oai-cn5g-udr (auth chain)
```

Deployment scenarios in `oai-cn5g-fed/docker-compose/`:
- Basic (NRF + AMF + SMF + UPF + AUSF + UDM + UDR)
- With NSSF (network slicing)
- With PCF (policy)
- With NWDAF (analytics)
- With UPF-VPP (high-performance data plane)

## Conventions & Special Patterns

### Agent / Skill File Layout

The workspace follows a consistent agent customization pattern:

```
.github/skills/<skill-name>/
    SKILL.md                    ← Loaded by Copilot when skill activates; contains methodology
    <agent-name>.agent.md       ← Canonical agent definition (name, description, tools, instructions)

.github/agents/
    <agent-name>.agent.md       ← Symlink OR copy of canonical file (VS Code auto-discovery)
```

- **Skills** (`SKILL.md`) contain methodology, templates, and domain knowledge.
- **Agents** (`.agent.md`) bring skills together with identity, tool access, and constraints.
- Skills are referenced in the root `copilot-instructions.md` (custom instructions file) under a `<skills>` index so Copilot knows when to load them.
- Agents in `.github/agents/` are discovered by VS Code as `@<agent-name>` in chat.

## Supported 3GPP Features Summary

This is a high-level summary. For the authoritative per-layer feature list, see `openairinterface5g/doc/FEATURE_SET.md`. For per-NF compliance matrices, see `<nf>/docs/FEATURE_SET.md` in each NF directory.

### 5G NR gNB

| Category | Features |
|---|---|
| Frequency ranges | FR1 (15/30 kHz SCS, 5–100 MHz BW), FR2 (120 kHz SCS, 100/200 MHz BW) |
| Duplexing | Static TDD (configurable patterns), static FDD |
| MIMO | 4-layer DL, 2-layer UL (SU-MIMO); up to 4 TX/RX antennas |
| Modulation | Up to 256-QAM DL and UL |
| Channel coding | LDPC (BG1, BG2), Polar codes for control |
| PHY reference signals | DMRS type 1&2, PTRS, CSI-RS, SSB, SRS, PRS (Rel-16 positioning) |
| PRACH formats | Long formats 0/1/2/3; short formats A1–A3, B1–B3 |
| Random access | 4-Step RA (contention-based and contention-free), 2-Step RA |
| DL scheduler | Dynamic proportionally-fair; MCS from HARQ BLER or SINR |
| UL scheduler | Dynamic proportionally-fair; HARQ; MCS from PUSCH SINR |
| RLC | AM, UM, TM (TS 38.322 Rel.16) |
| PDCP | Ciphering and integrity (TS 38.323 Rel.16) |
| SDAP | QoS flow-to-DRB mapping (TS 37.324 Rel.15) |
| RRC | TS 38.331 Rel.17; setup, reconfiguration, reestablishment, handover |
| UE capacity | 16 UEs default; up to 64 with ≥40 MHz bandwidth |
| Handover | Intra-frequency and inter-frequency (measurement-gap-based) |
| CU/DU split | Supported — F1AP (TS 38.473 Rel.16) |
| CU-CP/CU-UP split | Supported — E1AP (TS 38.463 Rel.16) |
| O-RAN E2 | E2AP + E2SM-KPM + E2SM-RC via FlexRIC (integrated) |
| NTN | Rel-17: TA adjustment, Doppler compensation, 32 HARQ processes |
| RedCap | Initial Rel-17 support (SIB1 v17, RedCap/Normal UE coexistence) |
| GTP-U | N3 and F1-U; PDU Session Container; optional headers (TS 29.281) |

### 5G Core Network

| NF | Release | Key capabilities |
|---|---|---|
| AMF | Rel-16 (TS 23.501) | Registration, NAS, N2 termination, mobility, SEAF, location transport |
| SMF | Rel-16 | PDU session lifecycle, N4/PFCP to UPF, QoS, dynamic PCC |
| UPF | Rel-16 | GTPv1-U N3, PFCP, eBPF fast-path, slow-path kernel forwarding |
| AUSF | Rel-16 | 5G-AKA, EAP-AKA', MILENAGE/TUAK |
| UDM | Rel-16 | Subscription management, auth vector generation |
| UDR | Rel-16 | MySQL-backed data storage, SBI northbound |
| NRF | Rel-16 | NF registration/discovery, OAuth2 token authorisation |
| PCF | Rel-16 | AM policy, SM policy, PCC rules |
| NSSF | Rel-16 | Network slice selection (S-NSSAI) |
| LMF | Rel-16 | UE positioning (NR-PRS, LPP, NRPPA) |
| NEF | Rel-16 | AS session with QoS API, monitoring events |
| NWDAF | Rel-16 | Network data analytics (Python microservices) |

### Intentionally Not Implemented

- EPS (4G LTE Core) interworking with 5GC
- Non-3GPP access (Wi-Fi, WLAN interworking)
- Lawful intercept
- Charging (only partial CHF support)
- N14 (AMF-to-AMF for UE context transfer during idle-mode mobility across AMFs)
